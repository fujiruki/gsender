# AI専門家会議: gSenderのHoming失敗時UX設計の再検討

## 会議の定義

- **テーマ**: Homing失敗(ALARM 6-9)後のUX設計を、kglovern氏指摘のダイアログ詰み問題と、リミットスイッチ物理故障時の恒久ジョグブロック問題の両方を踏まえて再検討する
- **ゴール**: 設計レビュー＋意思決定(fable案2だけで先に進めるか、副次課題も含めた統合設計にするか、段階分けするか)
- **前提条件**:
  - 実機の安全インシデント対応として実装したF-05の趣旨(誤操作防止)は後退させない
  - `master`(自社フォーク・日本語UI)と`integration/dev-ja`(本家向けPR、英語のみ)の両方に影響し得る
  - 本家への提案は差分が小さいほど通りやすい(実績: PR #955は無競合cherry-pickで対応済み)
  - CLAUDE.mdのコーディングルール上、既存ファイルへの変更は最小限が原則
- **判断基準**: 安全性を犠牲にしないこと最優先、次に実装コスト・手戻りリスク、本家への通りやすさ

## 背景

1. 本家PR #953(F-05 Homing安全性修正)にメンテナーkglovern氏から指摘: ホーミング失敗(ALARM 6-9)後、Homeボタンは無効化されHomingできず、Unlockボタンを押すと「Unlock Anyway」の確認ダイアログが出て詰む(実際は完全ブロックではなくUnlock Anywayを選べば抜けられるが、警告文と矛盾するUX)。
2. fableへの調査依頼で案2(ダイアログの2択をRehome(既定・強調)/Unlock Anywayに変更)が提案された。diffは小さく(`features/UnlockButton/index.tsx`の`confirmUnlockAfterHomingFailure()`のみ)、kglovern氏の提案とも文言レベルで一致する。
3. fableの調査で副次的な問題も判明: `$22`(Homing cycle enable)が有効だがリミットスイッチが物理的に故障している機体では、Rehomeを選んでも必ず失敗するループになり、諦めてUnlock Anywayを選んでも、Jogging側の`canClick`判定(`hasHomed=false && $22>0`でブロック)により恒久的にジョグ不可のままになる。唯一の脱出路はConfig画面から`$22`を手動で0にすることだが、GUI上に案内が一切ない。

事実確認: ALARM 6-9の内訳(grbl準拠)
- ALARM:6 = ホーミング中のリセット
- ALARM:7 = ホーミング中のセーフティドア開放
- ALARM:8 = プルオフでリミットスイッチが解除できない(配線/スイッチ不良の典型)
- ALARM:9 = 探索距離内でリミットスイッチが見つからない(配線切れ/スイッチ故障の典型)

「物理故障」は主にALARM:8/9に偏って現れる可能性が高く、6/7とは性質が異なる。

## ラウンド1(Divergence)

**CNC安全UX専門家**
- 立場: fable案2だけでは不十分。ALARM種別による分岐案内を今回のスコープに含めるべき。
- 提案1: ダイアログはfable案2を採用しつつ、ALARM:8/9のときだけ「リミットスイッチの配線・故障を確認してください」という追加文言を出す(状態管理の追加は不要、`GRBL_ALARMS`の番号を見るだけで実現可)。
- 提案2(意外性): 「Unlock Anyway」を選ばせる設計自体を見直し、ALARM 6-9解除後は自動的に「制限付きジョグモード」(低速・小刻み移動のみ許可)に落とす。
- 懸念: 提案2はdiffが一気に膨らむ。

**ソフトウェア設計者**
- 立場: 副次課題は今回のPRスコープに入れるべきではない。ダイアログ修正とジョグブロック条件の見直しは分離すべき。
- 提案1: fable案2のみを先に入れ、副次課題は別Issueとして切り出す。
- 提案2(意外性): `hasHomed`を`'unknown' | 'confirmed' | 'failed-hardware-suspected'`の3値にし、ALARM:8/9が連続発生したら`'failed-hardware-suspected'`に遷移させる。
- 懸念: 3値化は`GrblController.js`と`Jogging/index.tsx`両方の変更が必要で影響範囲が広く、本家レビューで「複雑にしすぎ」と見られるリスク。

**OSSコントリビューション戦略家**
- 立場: 本家に出す提案とフォーク独自実装は明確に分けるべきで、今回本家に出せるのはfable案2程度が限界。
- 提案1: fable案2は英語のみでPR #953に追記コミット、副次課題は`master`限定の独自拡張として本家には出さない。
- 提案2(意外性): 逆に副次課題こそ本家にIssueとして先に投げ、kglovern氏を巻き込んで方針をすり合わせてから作る。
- 懸念: Issueへの反応が遅ければ自社対応が方針待ちで止まる。

**悪魔の代弁者**
- 立場: 「ダイアログだけ直して副次課題は後回し」という折衷案そのものに反対。中途半端な安全機構強化が今回の火種であり、生煮えのまま追加修正を重ねるのは危険。
- 提案1: 一旦立ち止まりF-05全体を実機で再検証してから追加修正すべき。
- 提案2(意外性): ジョグブロックは「警告表示のみ」に格下げし、実際の移動阻止はしない方が、詰みによる二次被害(強制Unlock Anyway濫用)より安全という逆説を取る。
- 懸念: 本家の安全思想と真っ向から矛盾し、提案として通らない可能性が高い。

### トレードオフ

- 文言案内+Config導線は安全性を後退させずに詰みの体感を改善できるが、根本原因(リミットスイッチ故障の検知・修理)自体は解決しない応急処置。
- `hasHomed`の3値化のような根本的な状態設計見直しは、将来Operator Plugin構想でホーミング状態管理を本格的に扱う機会があれば再検討する価値がある。
- 本家Issue提起は自社実装をブロックしないが、本家の設計思想を確認せずに自社だけで作り込むと、後で方向性の相違が発覚するリスクがある。

### 簡易プレモーテム

6ヶ月後に失敗していたとしたら、最も疑わしいのは、案内文言を読んでもConfig画面の`$22`項目にたどり着けないユーザーが一定数残り、サポート問い合わせが減らなかったケース。文言だけの案内はナビゲーションの複雑さ(Config画面の階層、`$22`という設定番号の分かりにくさ)を解決しないため、「案内はしたが実効性がなかった」という失敗が最も起こりやすい。

## 最終結論

**結論: 条件付きYes(段階分け)**

1. **即実装(今回のPRスコープ)**: fable案2(ダイアログのRehome既定化)+ ALARM:8/9限定の追加案内文言(配線・スイッチ故障の可能性 + Config画面から`$22`を無効化できる具体的な導線まで文言に含める)。`master`・`integration/dev-ja`双方に反映、`contrib/`ブランチとしてPR #953に追記コミット。
2. **並行(実装をブロックしない)**: 本家にIssueを立て、「ALARM 8/9が繰り返し発生するケースをどう考えるか」kglovern氏に方針を尋ねる。回答を急がず、自社実装は1を先に進める。
3. **今回は見送り**: `hasHomed`の3値化・制限付きジョグモード・ブロック撤廃は影響範囲・安全性リスクの観点で時期尚早。将来Operator Plugin構想での検討候補として記録。

**採用理由**: 安全性を後退させず、実装コストを小さく保ちながら、「原因は伝えるが対処法を伝えない」という中途半端さを解消できる。

**棄却案とその理由**: 上記「今回は見送り」参照。工数対効果・本家レビューへの通りやすさ・状態管理の複雑化リスクの観点で今回のスコープに合わない。

**想定リスクと対策**: 「文言だけでは実効性が不足する」リスクに対し、案内文言に具体的なConfig画面への行き方まで含めることで一定緩和。それでも改善しなければ次フェーズでConfig画面への直接リンクを検討。

**少数意見**: 悪魔の代弁者の「ブロックを厳しくするほど安全という前提そのものが火種」という視点、CNC安全UX専門家の「制限付きジョグモード」は、Operator Plugin構想での状態管理見直し時に再検討する価値がある。

**確信度**: 中。ALARM:8/9が実際に「物理故障」に偏っているかはgrbl定義からの推測であり、実機発生頻度データはまだない。
