## i18n設計方針（fable設計提案 + kaigiレビューで確定）

### ライブラリ選定: react-i18nextは導入しない

- `package.json`の`i18next ~15.0.9`はサーバー側Express用(`i18next-fs-backend`, `i18next-http-middleware`)。react-i18nextを使うにはi18next v23+が必要で、アップグレードするとサーバー側依存に波及するリスクがある
- 英日2言語・複数形処理不要という規模に対し、react-i18next導入は過剰投資と判断（kaigi結論）

### 実装: 自前t()関数 + 英文キー方式

```
src/app/src/i18n/
  index.ts          # t() / initI18n() / setLanguage()
  i18n.test.ts
  locales/
    ja.json          # { "Start Job": "ジョブ開始", ... } キーは英文そのもの
```

- `t(key, vars?)`: `table[key] || key`でフォールバック（未翻訳は英語表示）。`{{name}}`補間はi18next互換記法とし、将来react-i18next化する場合も呼び出し側は無変更で済むようにする
- 言語切替は`workspace.language`をstoreに保存し、**次回起動時に反映**（実行時切替は対象外。データ定義ファイルがモジュールレベルで評価されるため、実行時切替は複雑さに見合わない）
- `initI18n()`で`document.documentElement.lang = 'ja'`を設定（Chromiumが漢字に中国語フォントを当てるのを防ぐため必須）

### 未翻訳・孤立キー検出: scripts/i18n-sync.mjs

- 対象: `src/app/src/**/*.ts,tsx`（`*.test.*`, `mocks/`, `tests/`, `i18n/`は除外）
- 抽出パターン: (A) `t('...')`リテラル呼び出し、(B) データ定義ファイル(`SettingsMenu.ts`)の`label:`/`description:`文字列リテラル
- 検出結果:
  - **NEW**: コードにあるがja.jsonに無い → `""`で追記
  - **ORPHAN**: ja.jsonにあるがコードに無い（本家の文言変更の疑い）→ bigram類似度で改名候補を提示、`exit 1`
  - **untranslated**: ja.json内で値が`""`のまま
- `npm run i18n:sync`（書込あり）/ `npm run i18n:review`（対訳表をmarkdown出力、書込なし）
- rebase後の運用: `git rebase upstream/main` → `npm run i18n:sync` → ORPHANが出たら改名候補を確認しキーを付け替え → NEWの翻訳を埋める → `exit 0`確認 → テスト → commit

#### 抽出ロジックの制約（2026-09-17 Codex調査で判明）

`i18n-sync.mjs`はASTパーサーを使わず、正規表現`T_CALL`で`t('...')`呼び出しのみを走査する。**JSXの生テキストノードは一切抽出しない**ため、「JSX内で複数行に折り返された文言が検出漏れになる」という現象は起こり得ない（そもそもJSX生テキストを見ていないため）。過去にこの仮説で説明していた不一致は、以下のどちらかに起因すると考えられる:

1. `t(...)`呼び出し自体に実改行・連続空白が含まれ、`unescape()`（`\n`エスケープの変換のみ、空白のcollapse/trimは一切しない）では正規化されず、微小な空白差で別キー扱いになる
2. そもそも該当箇所が`t()`化されていない生JSXテキスト（このツールの原理上検出不可能）

`${var}`テンプレートリテラルは`m[2].includes('${')`で検出されると`WARN dynamic key (cannot sync)`を出して同期対象外にスキップされる（意図的な仕様）。`${var}`→`{{var}}`への機械変換は、正規表現ではテンプレート式の境界（ネストした`{}`・関数呼び出し・条件式等）を安全に判定できないため、単純な`${identifier}`パターンに限定するか、AST変換に切り替える必要がある。

改善する場合の方針: `add()`前に`unescape(raw).replace(/\s+/g, ' ').trim()`のような正規化関数を一律適用する（既存`ja.json`側のキーにも同じ正規化をかけないと`in`/`has`の完全一致比較が壊れるため、両側同時に変更する）。生JSXテキストの検出が必要なら正規表現をASTベース(JSXText)に置き換える必要がある（現状は未着手）。

### rebase耐性のための設計原則

- 既存ファイルへの変更は「`import`1行 + `t()`ラップ」に限定し、構造変更・整形変更を混ぜない
- 基盤コミット / `t()`ラップ(機能ディレクトリごと) / `ja.json`翻訳、の3種類でコミットを分離する
- `t()`のシグネチャをi18nextの`t(key, options)`の部分互換にしておき、本家が将来react-i18nextを採用した場合も呼び出し側コードは無変更で載せ替えられるようにする

### レイアウト崩れ対策（日本語特有）

- `document.documentElement.lang = 'ja'`は必須
- `whitespace-nowrap` × 固定幅`w-[Npx]`の組み合わせ（フロント内49件）は実機で崩れた箇所のみ`min-w-`や`truncate`に修正する（全件は事前に直さない）
- ツールバー/タブ/ボタンは短い訳語を優先（Start→開始、Home→原点復帰、Probe→プローブ 等）

### 開発用サーバーポートの環境変数化（2026-09-17、F-07関連）

このbackPCでは実機CNC接続用サーバー（`start-gsender.bat`経由の`npm run start-dev`、ポート8000固定）が常時稼働しており、`npm run electron:hot`の内部で起動する開発用サーバー（`start-dev:nodemon`）も同じポート8000をハードコードしていたため、両者が衝突する。これを避けるため、以下を環境変数`GSENDER_DEV_PORT`で上書き可能にした（未設定時は従来通り8000、既存の`start-gsender.bat`の挙動に影響なし）。

- `src/server-cli.js`のデフォルトポート算出（`GSENDER_DEV_PORT`未設定時は8000）
- `src/app/vite.config.js`の`/api`・`/socket.io`プロキシ先（開発用サーバーと同じポートを向くように、こちらも同じ環境変数を参照）
- `package.json`の`start-dev`・`start-dev:nodemon`から明示的な`-p 8000`指定を削除し、上記デフォルト値に委ねる形に変更

実機サーバー稼働中に`electron:hot`の実起動確認を行う場合は、例えば`GSENDER_DEV_PORT=8099 npm run electron:hot`のように別ポートを指定する。

## ビルド/テスト時間の計測（R-002）

`npm run build` / `npm run test:app`等の主要コマンドの所要時間を計測し、履歴を残す仕組みを追加する。目的は、i18n化の作業を重ねるうちにビルド・テストが遅くなっていないかを把握し、遅ければ工程自体の改良を検討する材料にすること。

- `scripts/measure-time.mjs <label> -- <command...>`: 任意のコマンドをラップして実行時間を計測し、`perf-log.csv`（プロジェクトルート、gitignore対象）に`日時,label,秒数,exit code`で追記する軽量スクリプト
- 既存の`build`/`test:app`スクリプト自体は変更せず、計測用の別スクリプト（例: `npm run build:timed`, `npm run test:app:timed`）として追加する（変更範囲を絞る方針を優先）
- 高度な計測基盤（CI連携、グラフ化等）は今回は作らない。まずは実行のたびに手元でログが積み上がる最小構成にする

## ブランチ運用（2026-09-16改定）

ChatGPT＋晴樹さんの決定（AI共有庫カンガルー`2026-09-16_05_gSender_本家追従_日本語安定版_PR運用_ブランチ設計_決定記録.md`）に基づき、3線運用に改める。**本家のアクティブ開発ブランチは`upstream/main`ではなく`upstream/dev`**（2026-09-16時点でPlugin SDK一式もここに存在することを確認済み。旧記述の`upstream/main`は誤り）。

**発注者の方針（2026-09-16、本人の言葉で確認）**: 「本家の開発に協力したい。本家の最新コミットを読みながらPRを送れるように開発しつつ、あちらの開発が間に合わない日本語化はこちらのプロダクトには適用された状態で利用する」。つまりOperator Plugin開発の副産物としてPRを検討するという受動的な姿勢ではなく、**`integration/dev-ja`で本家`upstream/dev`を継続的に追う過程そのものを本家貢献の機会として能動的に活用し、日本語化資産は本家の対応状況に関わらず常に自社プロダクトへ適用された状態を保つ**、という二本立てが基本姿勢。ブランチ運用は既にこの方針を体現する設計になっているため変更なし。

| ブランチ | 役割 | 運用 |
|:--|:--|:--|
| `master` | 現場安定線。藤田建具店の日本語版として当面維持 | 重大な不具合修正以外の新規開発はしない |
| `integration/dev-ja` | 次期本命線。`upstream/dev`起点で新規作成し、日本語化資産(`ja.json`1639件等)を再適用する土台 | 本家追従は`upstream/dev`を**merge**（force-rebaseは常用しない）。追従毎に未翻訳検出・型チェック・主要テスト・スモークテストを行う |
| `contrib/<topic>` | 本家へのPR専用 | 必ず最新`upstream/dev`から切る。1PR=1論点、自社専用仕様を混ぜない。送信直前に`upstream/dev`へrebase |

`master`の24 aheadコミットは丸ごとcherry-pickせず、A(日本語化中核として再適用)/B(開発支援・必要なら再作成)/C(履歴として残すのみ)/D(本家へ返せる汎用修正候補)に分類して扱う。`master`→`integration/dev-ja`への切替条件・切替時の`archive/ja-legacy-*`退避方法は決定文書を参照。
