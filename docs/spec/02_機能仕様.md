## F-01: i18n基盤 + 接続画面日本語化(M0)

### 概要

自前のi18n基盤(`src/app/src/i18n/`)を新設し、未翻訳・孤立キー検出スクリプト(`scripts/i18n-sync.mjs`)を用意する。基盤の動作確認を兼ねて、まず接続画面(TopBar/Connection)を日本語化する。

### 入力

発注者が設定画面で言語を「日本語」に切り替え、gSenderを再起動する。

### 処理

1. 起動時に`workspace.language`をstoreから読み込み、`ja.json`をロード
2. `document.documentElement.lang = 'ja'`を設定
3. 接続画面のコンポーネントで`t()`を用いてラベルを表示

### 出力

接続画面（ポート選択・接続ボタン・ステータス表示等）が日本語で表示される。

### ビジネスルール

- 既存ファイルへの変更は「`import`1行 + `t()`ラップ」に限定する
- `SettingsMenu.ts`等のデータ定義ファイルは編集しない（詳細は`05_技術設計.md`）

### エラーケース

| 条件 | 挙動 |
|:--|:--|
| ja.jsonにキーが無い | 英語表示にフォールバックする |
| `t()`内で動的キー(`` t(`...${x}`) ``)を使っている | `i18n-sync.mjs`がWARNを出し同期対象外とする |

### 完了条件

- ja起動で接続UIが日本語表示になる
- `npm run test:app`が通る
- `npm run build`が成功する
- パッケージ化バイナリを実機CNC（無ければgrblHALシミュレータ）に接続し、接続→ジョグ→切断が日本語UIで完了する
- `npm run i18n:sync`がexit 0（NEW/ORPHANゼロ）

## F-05: Homing安全性修正(hasHomed判定バグ)

### 概要

2026-09-16、実機でShift+←キーによるX軸ジョグ中にX軸リミットスイッチが物理破損する安全インシデントが発生した。GRBLログ解析の結果、接続時に`$H`(Homing)を実行したが`ALARM:8 (Homing fail)`で失敗しており、ユーザーは`$X`でアラームを解除して操作を続けていたことが判明した。原因調査の結果、日本語化フォーク固有ではなく`upstream/dev`ベースの本家コード自体に存在する欠陥と判明した（`integration/dev-ja`上で確認済み。詳細は本セクション末尾の調査結果を参照）。

欠陥は2箇所:
1. `GrblController.js`の`hasHomedSet`判定: `$H`送信後に届いた最初のステータスが`Alarm`であっても`hasHomedSet`を`true`にセットしていた。ホーミング失敗時も「成功扱い」になっていた
2. ジョグ許可判定(`Jogging/index.tsx`の`canClick`/`canClickShortcut`): 接続状態とactiveState(`Idle`/`Jog`)のみで判定しており、`hasHomed`をそもそも参照していなかった

事故の流れ(`ALARM:8`→`$X`でUnlock→`Idle`→ジョグ操作が素通り)はこの欠陥と完全に整合する。

### 入力

GRBLからの`$H`実行後のステータス応答、および`ALARM:n`応答(nはアラームコード)。

### 処理

`GrblController.js`（`src/server/controllers/Grbl/`、grblHAL版`GrblHalController.js`はリアルタイムの`H:`フィールドで判定しており本欠陥は無い）に対し、以下3点を修正する:

1. **hasHomedの成功判定修正**: `runner.on("status")`ハンドラで、`$H`送信後最初のステータスの`activeState`が`Alarm`の場合は`hasHomedSet`を`true`にしない
2. **ALARM:6-9受信時のリセット**: `runner.on("alarm")`ハンドラで、アラームコードが6〜9(いずれも"Homing fail"系。`constants.js`の`GRBL_ALARMS`参照)の場合、`hasHomedSet`を`false`にリセットする（過去に成功したホーミングが古い情報として残っているケースに対応）
3. **確認モーダルの追加**: ALARM:6-9でのアンロック($X)実行前に、確認ダイアログを表示する。既存の共通ダイアログ機構(`app/components/ConfirmationDialog/ConfirmationDialogLib`の`Confirm()`)を使い、`app/features/UnlockButton`に`confirmUnlockAfterHomingFailure()`を新設。ライブなアンロック導線2箇所(`UnlockButton.unlockFirmware`、`MachineStatus`のローカル`unlock`ハンドラ)の両方から共通で呼び出す

`Jogging/index.tsx`の`canClick`/`canClickShortcut`自体は本タスクでは変更しない（今回のスコープはhasHomed判定の是正とアンロック時の警告に限定し、ジョグ許可判定へのhasHomed導入は影響範囲が広いため別タスクとする）。

### 出力

- ホーミング失敗時、`hasHomed`(Redux `state.controller.hasHomed`)が正しく`false`のままになる
- ALARM:6-9をアンロックしようとすると「Homing Not Complete / 原点復帰が未完了です」の確認ダイアログが表示され、「Unlock Anyway / それでもロック解除」を明示的に選択しない限り`$X`が送信されない

### ビジネスルール

- 修正対象は`GrblController.js`（plain Grbl）のみ。`GrblHalController.js`(grblHAL)は既にリアルタイムの`H:`フィールドで`hasHomed`を追従しており本欠陥は存在しない
- 新規UI文字列(`Homing Not Complete`, 確認文, `Unlock Anyway`)は日本語化フォークの慣習に従い`t()`でラップし`ja.json`に追加する

### エラーケース

| 条件 | 挙動 |
|:--|:--|
| ALARM:6-9でアンロックを試みる | 確認ダイアログを表示し、「Unlock Anyway」を選ぶまで`$X`を送信しない |
| ALARM:1,2,10,14,17（リミット系） | 従来通り`reset:limit`。本修正の対象外（別カテゴリのアラーム） |
| ALARM:11 / 'Homing'（Homing required） | 従来通りホーミング実行導線。本修正の対象外（Homing fail(6-9)とは別カテゴリ） |

### 完了条件

- [x] `upstream/dev`ベースの`integration/dev-ja`上のコードに同一欠陥が存在することを確認済み（`hasHomedSet`判定・`canClick`/`canClickShortcut`とも本家由来のまま）

## F-06: 改善要望送信機能(フィードバックウィジェット)

### 概要

gSenderの任意の画面から改善要望をその場で送信できるフィードバック機能。画面上に常設のフローティングボタンを置き、押すとモーダルが開く。要望本文・画像(複数)・優先度を入力して送信すると、同一PC上のgSenderサーバーが保有するローカルDBに保存される。指揮AI(このbackPC上のClaude Code)がDBを直接読み取り、対応したレコードには「導入済み」フラグを立てる。

**この機能は藤田建具店フォーク限定のオリジナル機能であり、`contrib/<topic>`・本家PRには一切含めない**（ユーザー明示指示、2026-09-17）。`master`にのみ実装する。`integration/dev-ja`（本家追従の次期線）には含めない。

### 入力

- 要望本文（テキストエリア、必須）
- 添付画像（0枚以上、複数可）。ファイル選択、またはテキストエリアへの貼り付け（Ctrl+V等でクリップボード画像を検出しファイル化）の両方に対応
- 優先度（高・中・低のいずれか、必須。デフォルトは中）

### 処理

1. 画面右下（全画面共通のレイアウト、既存のトースト表示等と被らない位置）にフローティングボタンを常設表示する
2. ボタン押下でモーダルを開く。モーダルは既存の共通ダイアログ機構（`ConfirmationDialogLib`等）と統一感のあるスタイルにする
3. テキストエリアの`onPaste`イベントでクリップボードの画像データを検出し、添付画像として追加する（`clipboardData.items`のimage/*タイプを判定）
4. 添付画像はサムネイル一覧として表示し、各サムネイルの右上に削除(×)ボタンを表示する
5. 送信時、現在の画面（ルート）を判別してレコードに含める
6. サーバー側APIへPOSTし、本文・画像・優先度・送信元画面・送信日時を保存する
7. 送信成功後、モーダルを閉じてトースト等で完了を通知する

### 出力

- ローカルDBに1件のレコードが追加される
- モーダルが閉じ、送信完了がユーザーに通知される

### データモデル（1レコードあたり）

| フィールド | 内容 |
|:--|:--|
| id | 一意なID |
| body | 要望本文（テキスト） |
| images | 添付画像ファイルへの参照（複数、パスまたはファイル名の配列） |
| sourceScreen | 送信元の画面（ルート名やパス） |
| priority | `high` / `medium` / `low` |
| createdAt | 送信日時（ISO 8601） |
| resolved | 指揮AIが取り込み・対応済みかを示す真偽値フラグ（初期値`false`） |
| resolvedAt | フラグが立った日時（任意、フラグ更新時に記録） |

### ビジネスルール

- DB・画像ファイルの保存先はリポジトリ外（gitignore対象）とし、コミットに含めない
- 既存の依存関係（`electron-store`または`jsonfile`、いずれも`package.json`に既存）を再利用し、新規のDBライブラリ依存を追加しない（軽量なファイルベースで十分な想定件数のため）
- サーバー側APIは既存の`src/server/api/`のパターン（`api.jobstats.js`等）に倣い`api.feedback.js`として追加する
- `resolved`フラグの更新は、指揮AI（Claude Code）がDBファイルまたは専用APIを通じて行う（UIから発注者が手動でチェックする機能は不要）
- 新規UI文字列は本フォーク独自機能のため、既存の日本語化コーディング規約（`t()`ラップ）に従って日本語化する

### エラーケース

| 条件 | 挙動 |
|:--|:--|
| 本文が空のまま送信しようとする | 送信を無効化（ボタンdisabled等）し、送信させない |
| 画像添付なしで送信 | 許可する（画像は任意） |
| DB書き込みに失敗 | エラートーストを表示し、モーダルは閉じない（再送信できるようにする） |

### 完了条件

- 任意の画面からボタン→モーダル→送信の一連の操作ができる
- 画像を複数枚、ファイル選択とクリップボード貼り付けの両方で添付でき、個別に削除できる
- 送信したレコードがローカルDBに、本文・画像・送信元画面・優先度・日時・`resolved:false`で保存される
- 指揮AI側からDBを読み取り・`resolved`フラグを更新できる
- `npm run test:app`・`npm run build`が通る
- `master`にのみ実装され、`integration/dev-ja`・`contrib/<topic>`には含まれない

## F-07: Electron本体のWindows起動修正

### 概要

`npm run electron:hot`（ホットリロード開発用のElectron起動コマンド）がWindowsで起動しない。`package.json`の`electron:hot`スクリプトが、Viteサーバーの起動待ち処理を`bash -lc '...'`で書いており、これがconcurrently経由でWindowsのデフォルトシェル(cmd.exe)に渡されるとシェル互換性の問題で失敗する。現状は`start-dev`（ブラウザ表示）で代替している。

### 現状のスクリプト（`package.json`）

```
"electron:hot": "npm run build-dev && concurrently --kill-others-on-fail --names \"esbuild,server,vite,electron\" \"npm run watch-dev\" \"npm run start-dev:nodemon\" \"npm run vite:dev\" \"bash -lc 'until curl -sf http://127.0.0.1:5173 >/dev/null; do sleep 0.2; done; cross-env NODE_ENV=development ELECTRON_RENDERER_URL=http://127.0.0.1:5173 electron ./output/main'\""
```

`bash -lc`部分は「Vite dev serverが起動するまで`curl`でポーリングし、起動したら`electron`を起動する」という処理。

### 処理方針

- `bash -lc`によるポーリングを、クロスプラットフォームで動く方式に置き換える（例: `wait-on`パッケージでVite dev serverの起動を待つ、または同等の小さなNode.jsスクリプトを`scripts/`に追加する）
- 新規依存を追加する場合は軽量なもの（`wait-on`等）に留め、自前実装より既存の定番パッケージを優先する
- macOS/Linuxでの既存の動作を壊さない（クロスプラットフォームで同じスクリプトが動くこと）

### ビジネスルール

- Windows(このbackPC含む)・macOS・Linuxのいずれでも`npm run electron:hot`でElectronアプリが起動すること
- 本家`upstream/dev`の`package.json`にも同じ`bash -lc`依存が存在するか確認し、存在する場合は本家PR候補として記録する（本家に存在しなければ日本語化フォーク固有の変更に起因する可能性があるため、その旨を報告する）

### 完了条件

- このbackPC(Windows)で`npm run electron:hot`を実行し、Electronウィンドウが実際に起動することを確認する
- `npm run test:app`・`npm run build`が通る
- `master`に実装する（本家に同じ問題があり著しく汎用的な修正であれば`contrib/<topic>`候補としてよいが、PR送信は別途承認を得る）
